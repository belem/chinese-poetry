## 本 Fork 的数据修正

本仓库 fork 自 [chinese-poetry/chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)。原数据爬取自网络，存在大量乱码、缺字与重复。本 fork 以古籍检索为证据做了系统性修正，并去掉了唐诗部分的重复数据（见下文「对使用者的影响」）；JSON 字段格式不变，只在部分唐诗记录上新增了 `prologue`；每一处改动都记录在 [`fix_progress.json`](fix_progress.json) 中（原文、改后、依据出处）。

### 修正原则

- **以古籍为证，不凭印象**：主要依据[识典古籍](https://www.shidianguji.com)中的古籍刻本、抄本的文字，辅以搜韵、古文岛、汉典；找不到可靠依据的标记为 `needs_review`，不作猜测。
- **不以通行本改底本**：课本或选本的写法不等于原文。
- **保留原字形**：只改动出错的字，并沿用本库已有的写法（如 搊 而非类推简化的 𫼝）。

### 对使用者的影响

- **删除 `御定全唐詩/`**：它与 `全唐诗/` 中的唐诗是同一部《全唐诗》的两份录文，对勘完成后不再保留（上游仓库仍有）。上表中 全唐诗 一侧的修正都保留在 `全唐诗/` 里。
- **唐诗选本并入全唐诗，去掉重复**（逐首记录见 [`docs/唐诗去重.tsv`](docs/唐诗去重.tsv)）：
  - 删除 `全唐诗/唐诗三百首.json`：它是从 `poet.tang.*` 抽出的副本，且有 3 首署名有误（如金昌绪《春怨》记作宋僧释明辩）。366 首都已在 `poet.tang.*` 中找到，标签并入原记录，按 `tags` 中的「唐诗三百首」筛选即可。
  - `水墨唐诗/` 中能在全唐诗找到的 172 首，在 `poet.tang.*` 原记录上加标签「水墨唐诗」并带上赏析 `prologue`。文件只留下全唐诗未收或改写较多的 4 首（如杜牧《清明》）。
  - `poet.tang.*` 删除 548 首同时收在 `五代诗词/huajianji/`（花间集）或 `五代诗词/nantang/`（南唐二主词）中的同一作者的同一首词，以带词牌结构的选本为准。作者不同的属于归属异说，两边都保留，如《应天长》李璟／李煜。
- **补入 poem-wechat 语料中本库确实没有的 65 首**：拿上游 11 个带正文的集子（2360 条）按**正文**逐条判重（不按标题——上游「感遇·其一」其实是全唐诗「感遇十二首 四」，按题名对会漏一大片），正文全同或前 12 字全同的一律不收。剩下本库确实没有的 65 条补进来，各自成目录，逐条记录见 [`docs/wechat_corpus_collect.tsv`](docs/wechat_corpus_collect.tsv)：
  - `近现代诗/`（41 首）：课本里的近现代诗（毛泽东、鲁迅、艾青、余光中等）以及几篇文言课文（《三峡》《核舟记》《劝学》），本库原来没有这一块。
  - `近现代诗/元明清詩.json`（8 首）：课本选目的元明清绝句（袁枚、秋瑾、戚继光等），进不了 `古诗源/`（那部书到隋为止），仍归入这本横跨朝代的诗选。
  - `宋词三百首/`（4 首）：本库 `tags` 里的「宋词三百首」有 280 首，缺的 20 首里，清词（纳兰性德、夏完淳）与个别宋人僻调（查荃《透碧宵》）本库此前一首都没有；其余多为已有作品的异文，按「题同文异两存」不收。
  - `文选/`（9 首）：《文选》所收西晋诸家的诗，本库全唐诗只收唐人，这块是空的。
  - `古文观止/`（1 首）、`乐府诗集/`（2 首）：零星的缺篇；两部书的其他篇目本库已有，按目录并入，不另立重复目录。
  - 课内、近现代、古诗非唐、节日节气这几部是横跨朝代体裁的课本选目，不是一部书，按体裁并入上面的目录，没有各自开目录。
- 仍有约 130 个文件含待复核项（主要是底本原有的 `□` 缺字，以及古籍中也无法确认的乱码），详见 `fix_progress.json` 中 `corrected` 为 `null` 的条目。`全唐诗/error/` 是上游标出的问题数据，不在发布范围内，标记为 `out_of_scope`。

### 工具与参与

- [`scripts/check_structure.py`](scripts/check_structure.py)：全库质检（乱码、缺字、诗句与词牌字数异常），只报告不修改。
- [`scripts/twin_collate.py`](scripts/twin_collate.py)：选本（花间集、唐诗三百首、千家诗等）↔ 全唐诗 / 宋词 互校，一字之差以识典古籍判定，人工审核后写回；已审条目记在 [`docs/小合集互校.applied.json`](docs/小合集互校.applied.json)。
- [`scripts/merge_anthologies.py`](scripts/merge_anthologies.py)：把唐诗选本并入全唐诗、删除重复（默认预演，`--apply` 写回）。
- [`scripts/shidian.py`](scripts/shidian.py)：以识典古籍批量检索为证据，生成审核表，人工确认后写回。
- [`scripts/wechat_corpus/`](scripts/wechat_corpus/)：对 poem-wechat 语料的判重与补录。`audit.py` 按正文判重出 `docs/wechat_corpus_audit.tsv`，`collect.py` 按上游 id 精确取正文复核、落库并登记（默认预演，`--apply` 写盘）。
- [`scripts/collate.py`](scripts/collate.py)：整部合集逐句与古籍对勘，由 GitHub Actions 每天定时分批运行。宋词对勘正在进行中，进度与参与方式见 [`docs/宋词对勘.md`](docs/宋词对勘.md)。
- 参与修正请阅读 [`AGENTS.md`](AGENTS.md)（适用于人工与 AI 贡献者）。

## 与 GitHub 的同步

本仓库是 [belem/chinese-poetry](https://github.com/belem/chinese-poetry) 的镜像：内容与上游 **逐字节一致**，只额外多出 `.cnb.yml` 和 `.cnb/` 两个同步配置。

两端都在 `develop` 分支上直接 commit，不走 PR。

| 方向 | 触发 | 动作 |
| --- | --- | --- |
| CNB → GitHub | `develop` 推送 | 直接 push 到 GitHub `develop` |
| GitHub → CNB | 每 6 小时 / 手动 | fast-forward 拉取 `develop` |

- `main` 不参与自动同步；上游默认分支是 `fix-typo`，本仓库固定用 `develop`。
- 只做 fast-forward。两侧分别推进导致分叉时任务失败，人工合并，绝不强推。
- 上游的 `.github/workflows` 原样保留，但在 CNB 镜像里不会运行；要跑对勘等定时任务请用 GitHub 侧。

### 凭据

GitHub PAT 存在密钥仓库 [npu-gpu-cpu/poem-source-secrets](https://cnb.cool/npu-gpu-cpu/poem-source-secrets) 的 `pair.yml` 里，由 `.cnb.yml` 各任务用 `imports` 引用后注入为环境变量。

- 字段名 `GITHUB_TOKEN` 或 `GITHUB_PAT` 都行，`sync.sh` 两者都认。
- PAT 需对 `belem/chinese-poetry` 有 **Contents: Read and write**。
- 密钥仓库禁止本地 clone / 推送，只能 Web 端改；引用放行条件由密钥仓库文件里的 `allow_slugs` 等字段控制，见 [文件引用](https://docs.cnb.cool/zh/build/file-reference.md)。
- 密钥仓库路径与文件名在 `.cnb.yml` 顶层环境变量 `SECRETS_SLUG` / `SECRETS_REF` / `SECRETS_FILE` 里改一处即可。

未注入时同步会跳过，日志打印 `[sync] 没有 GITHUB_PAT / GITHUB_TOKEN，跳过与 GitHub 的同步` 和排查提示；注入成功只打印凭据长度，绝不打印值。

### 手动触发

任务 `manual-sync`（事件 `api_trigger_sync`）支持手动运行，方向由环境变量 `MODE` 决定：

- `MODE=push`：CNB → GitHub
- `MODE=pull`：GitHub → CNB
- `MODE=both`：先拉后推（默认）

```bash
cnb build start-build --branch develop --event api_trigger_sync --env MODE=push
```

事件名不能写成裸 `api_trigger`：密钥仓库 `pair.yml` 的 `allow_events` 是 `api_trigger_*`，通配符不匹配自身，裸事件会在 Prepare 阶段被拒。

### 合并冲突提示

同一个 commit 若在两边都产生（比如 GitHub 侧的定时脚本改了文件、CNB 侧同时手动编辑），会形成分叉。此时先在本机把两侧 merge 成一个，再推 `develop`。
