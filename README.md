## 目录结构：先按朝代，再按书（或体裁）

顶层是 **14 个朝代目录**（与 [`dynasties/dynasties.json`](dynasties/dynasties.json) 的 `name` 一一对应），
外加一个 `汇编/`（跨代、没有单一主时段的书）：

```
先秦 汉 三国 晋 南北朝 隋 唐 五代十国 宋 元 明 清 近现 当   汇编
```

朝代下面是「一部书一个目录」（总集、别集、选本），或者按体裁分「诗 / 词 / 文」。选本不往总集里塞，
总集也不因为收的篇目跨代就往上提一层。**没有单一主时段的书放 `汇编/`**（《古文观止》跨周至明、
课本选目跨先秦至近现代），与 `先秦/诗文总集/` 是同一条道理。

```
先秦/
  诗经/  楚辞/  论语/  孟子/  大学/  中庸/          四书按书各占一个目录
  文/{zuozhuan, zhuangzi, daodejing, shanhaijing …}  子史佛经医书 34 部，从原来的「诗」里拆出
  诗文总集/{乐府诗集, 昭明文选}                    跨代诗歌总集，归它取材的主要时段
```

几条约定：

- **朝代目录用短名，与 `authors/dynasties` 的取值同一个值空间**：`晋` 不分东西晋，`南北朝` 不分南北，
  `近现` 指 1912—1949 年出生的作者，`当` 指 1949 年以后。春秋战国、秦、商、上古归 `先秦`；辽、金归 `宋`。
  想知道一首诗属哪个朝代，看目录名即可；不用再 join 作者表。
- **`历代/` 已经拆散**：haitang 补录的那一锅烩原来混着周秦汉晋南北朝隋唐宋元明清当代，现在按作者朝代落进
  上面各朝代目录（2026-10 这一轮搬了 3592 条，逐条见 [`docs/历代拆分.tsv`](docs/历代拆分.tsv)，
  说明见 [`docs/历代拆分.md`](docs/历代拆分.md)）。拆出来的文件叫 `poet.*` / `ci.*`，`poet.*` 里既有诗也有文。
- **跨代的书进 `汇编/`**：《古文观止》收周文至明文 222 篇、课本选目跨先秦至近现代，按作者朝代切会拆成七八份，
  按书名就查不到了，所以整部书放在 `汇编/` 下（[说明](汇编/README.md)）。《古文觀止》母本原在 `先秦/蒙学/`，
  与 `先秦/古文观止/` 是同一部书的两份正文；现在以母本为准，按卷切进 `汇编/古文观止/`，对不上的 49 篇留在
  `古文观止·补.json`（逐条见 [`docs/汇编归位.tsv`](docs/汇编归位.tsv)）。原 `先秦/课外经典/` 是把一章《山海经》
  和一段《宋史》编在同一个文件里的课本选目，不是一个集子名也不是一部书，整体移到 `汇编/课本选目/`。
- **跨代的诗歌总集归它取材的主要时段**：《乐府诗集》《昭明文选》都在 `先秦/诗文总集/`，因为两书所收以汉魏六朝为大宗；
  它们各自收到的唐诗、五代词，凡在 `唐/诗/全唐诗/` 已有同一首正文的，按「一件作品只留一份正文」删去（见 [`docs/`](docs/)）。
- **《全宋诗》在 `宋/诗/全宋诗/`，与《全唐诗》分开**：它原先是追加在 `唐/诗/全唐诗/` 里的一批
  `poet.song.*`，目录名与内容不符。现已拆出，文件名与编号（`poet.song.[0-254000].json`）沿用上游、不重新分片，
  `fix_progress.json` 的键与 `docs/*.tsv` 里的位置同步迁到新路径。
- **一件作品只留一份正文**。《古诗源》与《诗经》《楚辞》《全唐诗》《全宋诗》《全宋词》逐字相重的，删掉《古诗源》
  那一份，诗仍可在《古诗源》里查到——按选本查的入口是 `anthologies/` 的目次与记录上的 `tags`，不靠目录里留副本。
  原先从《古诗源》里摘句的 7 首《诗经》与《橘颂》，现在只保留《诗经》《楚辞》的全文版本。
- **别集也按朝代与体裁落位**：纳兰性德原来是根目录下的 `纳兰性德/纳兰性德诗集.json` 单文件（258 首里 219 首是词、
  39 首是诗，字段用 `para` 而非 `paragraphs`），现按体裁分成词、诗两份；词 219 首随后并入
  `清/词/ci.qing.json` 作 `tags: ["纳兰词"]`（与宋词三百首同一套做法），`纳兰词/` 目录已删。
  原文件在一处词牌与诗题混排：`拟古·高云媚春日`、`南海子·分弓列戟四门开`、`汤泉应制·…`、`拟冬日景忠山应制·…`
  十二首是七言绝句，「·」后是首句小题，不是词牌，按诗归。
- **选本切片随作者朝代走**：《古诗源》里唐代以前的留在 `汉/古诗源/`；宋、明、清的切片放在
  对应朝代目录，文件名一律 `古诗源·宋诗` 这种「书名·卷名」，一眼看得出出自哪部选本、归在哪个朝代。
- **词部只有一层目录**：`宋/宋词/` 就是《全宋词》那一个 dataset，不再套 `词/宋词/`。
- **加载入口是 `loader/datas.json`**：路径变了，dataset 的 key 不变，用 `PlainDataLoader` 的下游不必改代码。
  `宋/宋词/` 是一个 dataset（`songci`），明诗、清诗各一个（`gushi-yuan-ming`、`gushi-yuan-qing`）。
  纳兰性德一部别集按体裁拆成两个：`nalanxingde`（词）、`nalanxingde-shi`（诗），key 与 id 都留着，旧入口取到的仍是词。
- 目录与文件的移动只改路径，不动正文；`fix_progress.json` 的键同步改成新路径。

## 本 Fork 的数据修正

本仓库 fork 自 [chinese-poetry/chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)。原数据爬取自网络，存在大量乱码、缺字与重复。本 fork 以古籍检索为证据做了系统性修正，并去掉了唐诗部分的重复数据（见下文「对使用者的影响」）；JSON 字段格式不变，只在部分唐诗记录上新增了 `prologue`。`fix_progress.json` 只记录哪些文件查过、何时、由谁、结论如何，不保留逐条勘误日志——每一处改动看 git 历史即可，全库随时可用 `scripts/check_structure.py` 重查。

### 修正原则

- **以古籍为证，不凭印象**：主要依据[识典古籍](https://www.shidianguji.com)中的古籍刻本、抄本的文字，辅以搜韵、古文岛、汉典；找不到可靠依据的标记为 `needs_review`，不作猜测。
- **不以通行本改底本**：课本或选本的写法不等于原文。
- **保留原字形**：只改动出错的字，并沿用本库已有的写法（如 搊 而非类推简化的 𫼝）。

| --- | --- | --- |
| CNB → GitHub | `develop` 推送 | 直接 push 到 GitHub `develop` |
| GitHub → CNB | 每 6 小时 / 手动 | fast-forward 拉取 `develop` |

- `main` 不参与自动同步；上游默认分支是 `fix-typo`，本仓库固定用 `develop`。
- 只做 fast-forward。两侧分别推进导致分叉时任务失败，人工合并，绝不强推。
- 上游的 `.github/workflows` 原样保留，但在 CNB 镜像里不会运行；要跑对勘等定时任务请用 GitHub 侧。

### 凭据

GitHub PAT 存在内部密钥仓库的 `pair.yml` 里（路径见 `.cnb.yml` 顶层的 `SECRETS_SLUG` / `SECRETS_FILE`），由各任务用 `imports` 引用后注入为环境变量。

- 字段名 `GITHUB_TOKEN` 或 `GITHUB_PAT` 都行，`sync.sh` 两者都认。
- PAT 需对 `belem/chinese-poetry` 有 **Contents: Read and write**。
- 密钥仓库禁止本地 clone / 推送，只能 Web 端改；引用放行条件由密钥仓库文件里的 `allow_slugs` 等字段控制（文件引用语法见平台文档）。
- 密钥仓库路径与文件名在 `.cnb.yml` 顶层环境变量 `SECRETS_SLUG` / `SECRETS_REF` / `SECRETS_FILE` 里改一处即可。

未注入时同步会跳过，日志打印 `[sync] 没有 GITHUB_PAT / GITHUB_TOKEN，跳过与 GitHub 的同步` 和排查提示；注入成功只打印凭据长度，绝不打印值。

### 手动触发

任务 `manual-sync`（事件 `api_trigger_sync`）支持手动运行，方向由环境变量 `MODE` 决定：

- `MODE=push`：CNB → GitHub
- `MODE=pull`：GitHub → CNB
- `MODE=both`：先拉后推（默认）

```bash
cnb build start-build --branch develop --event api_trigger_sync --env MODE=push
```

事件名不能写成裸 `api_trigger`：密钥仓库 `pair.yml` 的 `allow_events` 是 `api_trigger_*`，通配符不匹配自身，裸事件会在 Prepare 阶段被拒。

### 合并冲突提示

同一个 commit 若在两边都产生（比如 GitHub 侧的定时脚本改了文件、CNB 侧同时手动编辑），会形成分叉。此时先在本机把两侧 merge 成一个，再推 `develop`。
