# 短 id 撞码：成因与修法

`id` 是记录身份（`scripts/backfill_ids.py` 文件头第 2 条）：由「作者 + 题名 + 正文 + 分段」
哈希出的 5–9 字符短码，全库唯一，搬目录、重排、重分片都不变号。

## 为什么会撞

2026-10/11 那批整本新书（三国演义、西游记、世说新语、笑林广记、三国志…）入库时，
各自单独跑过 `backfill_ids.py --apply` 的等价逻辑。脚本的发号顺序是**按 key 的字典序**，
与库里现存记录的顺序无关；`assign()` 手里的 `taken` 只有这一轮自己发出去的号，
写盘时又用「已是短 id 就不动」兜底。于是：

1. B 批发号时看不到 A 批已落盘的短码，两条不同的记录拿到同一个号；
2. 兜底那条规则只保证「重跑不改号」，不保证唯一，先落盘的两批于是谁也不让，
   全库留下 9 对撞码。

另一头，`assign()` 里「加长一位再试」的常规路径也走不到 —— 撞上了才发现，
那时两条都已写进文件。

## 修法

`scripts/backfill_ids.py` 改三处：

- `assign(keys, taken)` 接受「已占用」集合，`main` 把**库里全部现存短 id** 传进去，
  发号阶段就避开它们，一次收敛，重跑幂等；
- 写回循环的 `used` 集合发现「已是短 id 但撞了号」时，留先出现的一条，后来的按新号改掉，
  明细进 `docs/id去重.tsv`；
- `dump()` 不再整份重写：记录数与顺序没变时，只按旧文本换掉 `"id": "..."` 那几行
  （行型统计只是估计，碰上「某型尾空格占少数」的文件就会整片翻白）；没有改动就不写盘。
