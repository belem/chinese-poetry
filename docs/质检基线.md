# 质检基线与增量比较

`scripts/check_baseline.json` 是 `scripts/check_structure.py` 各类问题数量的基线：
数量比基线多，说明这批改动引入了新问题。

## 基线为什么天生是合并热点

基线是一个**全库总数**，而每个 PR 只改自己那几棵树。两个 PR 各修各的文件、各自把总数减下来、
各自把新基线写回：

| | 合并前 | A 合并后 | A 之后再合并 B |
| --- | --- | --- | --- |
| 各自的基线 | 6070 | 6010 | 6000 |
| 真实数量 | — | 6010 | 5990 |

先合并的那个是对的，后合并的那个必然错——它减数时没算上对方已经减掉的那部分。
行级冲突只是表象，改 `--allow-fewer`、加 `git checkout --ours` 都治不了：数字本身就是错的。
`docs/progress/` 拆成一文件一条解决的是同一类问题（整表重写必撞车），基线没法拆，只能换个口径。

## 现在的口径：PR 只判自己改动的文件

1. **PR 里不比全库。** `check_structure.py --files-from-diff <base>` 只检查本 PR 改动过的数据文件，
   跑十几秒而不是几分钟。
2. **基线从 develop 现取。** `--baseline` 读的是 `<base>` 那个提交里的 `scripts/check_baseline.json`
   （CI 里 `git checkout $BASE -- scripts/check_baseline.json`），不是本分支的。
   于是「只改了文件里本来就有问题的那些行」不会失败，新冒出来的问题才失败。
3. **数量下降不再要求写回基线。** 旧口径里数量低于基线也报错，本意是防止「基线比实际松、
   新缺陷藏在差额里」。现在差额由 CI 在主分支上每合并一次就抹平，不必再拿 PR 当触发器。
   旧口径「先给下限、再清理」的过渡阶段还想要这条路，可以本地跑
   `--baseline scripts/check_baseline.json --allow-fewer`，但不要写回基线。
4. **只有 CI 会写基线。** `data-quality.yml` 的 `refresh-baseline` 在 develop 每次 push 后重算并提交。
   它排在质检之后、不依赖质检结果：某一类已经在增加时，基线也要跟上，
   否则数字越挂越松，后面同类的退化合进来 CI 反而是绿的。
   代价是 `scripts/check_baseline.json` 的改动会显示成机器人提交，用 `git blame` 看不出原因——
   要追原因去看那次合并的 PR。

想手工核一遍全库（不必写回）：

```bash
python3 scripts/check_structure.py --show 3                              # 只看汇总
python3 scripts/check_structure.py --baseline scripts/check_baseline.json # 与本分支上的基线比
python3 scripts/check_structure.py --baseline-from origin/develop         # 与 develop 上的基线比
```

`--write-baseline` 只在确实要手工重算时用，正常流程交给 CI。

## 另一条路：干脆不要基线

也考虑过只做「增量」：只看 diff 里新增的行。问题在于语料的错法不是「新写了一行诗」，
而是「一行诗里的一个字被改坏了」——判不了删掉的那个字是不是比新写的更错，
所以仍要数一数改动文件的现状，再和一个数比。那个数还得存着，存着就还是基线。
把它交给 CI 维护、让 PR 只读不写，是这两条折中的落点。
